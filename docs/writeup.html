ContextGuard

A privacy layer that knows what your task actually needs

Today it's an app. The plan is to make it a service other agents call — the layer they go through, rather than one more thing competing with them.

The idea

Redaction tools ask "is this field sensitive?" That question has no good answer, because the same field is sensitive or not depending on why you're looking at it. ContextGuard asks a better one: does this task need it?

"Which item costs the most?"
Customer nameREMOVED
Bank accountREMOVED
Line itemsKEPT
"Which account do I pay?"
Customer nameREMOVED
Bank accountKEPT
Line itemsKEPT

Same invoice, same field, opposite decisions. That judgement is the part only a model can make — and the part everything else is built around.

How it works

your files → Claude decides what's private → code removes it → cleaned copy → Claude answers

Two separate agents with a hard boundary between them. The first reads your originals and produces a plan — never an answer. Deterministic code then executes that plan: it black-boxes image regions, deletes glyphs from PDFs outright rather than covering them, and strips metadata and annotations. The second agent receives only the cleaned copy.

Claude judges; code enforces. Sensitivity needs judgement, so a model decides it. Whether a file is allowed to leave is an invariant, so plain code decides that — the same way every time, with no room for persuasion. Anything the redactor can't fully clean is withheld entirely rather than released half-done.

The enforcement is close to free: on a text-layer PDF the gate, locator and redactor total 18 ms — under a tenth of a percent of the run. All the cost is the two model calls.

What's measured

An evaluation harness scores all six stages against ground truth across 29 tasks on invoices, HR records, banking forms and insurance claims.

MeasureResult
Correct answers from redacted context only100%
Sensitive regions successfully located100%
Task-required data preserved (no over-redaction)100%
Runs with zero leakage52%

The last number is the honest one. Every leak is the same class of thing — project references, claim IDs, employee IDs. The model reads "sensitive" as "personal data" and under-covers business identifiers. The fix is a hybrid detector: regex finds pattern-matchable identifiers at near-perfect recall, and the model is reserved for the necessity judgement it's uniquely good at.

The plan: become the layer, not the app

The valuable part isn't the answering agent — it's the sanitiser in the middle. Exposed as an MCP server, it becomes a tool any agent can call:

any agent → release_documents(files, task) → cleaned content + the decisions made

That inverts the risk. As agents gain outbound tools — databases, email, chat — each becomes a place private data can escape to. An agent that reads originals and holds those tools is one prompt injection away from exfiltration. Routed through ContextGuard, the agent holding the tools never possessed the sensitive data at all. It cannot leak what it never received.

The tool returns sanitised content, not file paths — so there is no filesystem for a caller to walk back through, and the boundary holds by construction rather than by instruction.

Getting there

  1. Close the coverage gap. Hybrid detection, then re-run the harness. 52% is not a number you expose across a tool boundary.
  2. Make the boundary structural. Delete the originals once the cleaned copy exists — closing both the sandbox gap and indefinite retention in one change.
  3. Extract the sanitiser. Split the pipeline so the redaction chain stands alone, answering optional. The existing app keeps working unchanged.
  4. Ship the MCP server. One tool, stdio transport, checked-in config so a team gets it on clone.
  5. Add destination awareness. The same document for the same question warrants different handling going to internal finance versus outside counsel.

The order matters. Steps 1 and 2 aren't features — they're the difference between a demo and something you'd point at real documents.

An MCP server built on a pipeline that leaks half the time doesn't contain the problem. It distributes it.
